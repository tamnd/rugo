# Changelog

What each release changed, why, and what it costs you. The versioning rules and what a section has to contain are in [RELEASING.md](RELEASING.md).

While the major is 0, a minor release may break anything, including the wire protocol and the command set.

Any number in here carries the machine and the profile it was measured on, or it does not go in. Nothing in this file was measured on a laptop.

## 0.1.0 — unreleased

Milestones `M0`, `M1` and `M2`: the workspace, the map and the server, plus the first half of `M3`. This is the first version that can be measured, and its memory has been measured against seven rivals. Its throughput has not.

### Added

- **A sharded Swiss table with a slab arena underneath it, in `rugo-map`.** One control byte and one four byte arena offset per slot, which is five bytes against the ten a Robin Hood bucket of one distance byte, three hash bytes and a six byte pointer costs. Probing is sixteen slots at a time under NEON, sixteen under SSE2 and eight at a time word-at-a-time everywhere else, so the narrower metadata is not a trade against speed. Entries are packed head to tail in a per-shard arena addressed by `u32` with no allocator header, which is the eight to sixteen bytes a `malloc` per entry costs. Key and value lengths are varints, and the expiry and the user flags are only there when a header bit says they are, so the ordinary entry header is three bytes.
- **An arena reserve that costs address space rather than memory.** The part of the newest segment nothing has been written into yet was the largest single item of overhead in the cache: eight of the twenty-eight bytes an entry rugo cost over its payload at ten million keys, and seven per cent of everything the arena held. A segment is now its own anonymous mapping, so a page of it costs nothing until an entry is written to it. Segments double again as a result, because the rule that made them grow by a sixteenth existed only to keep that reserve small and a mapping is a kernel object there is a limit on the number of. Measured on `gpc` the overhead went from 27.8 bytes an entry to 20.4. Windows and Miri keep the boxed slices and pay the reserve, which is why the memory gate now has a threshold for each and each one names the mechanism it bounds.
- **A memory test that is a gate rather than a claim.** `crates/rugo-map/tests/memory.rs` fills the map at several sizes and shard counts and fails if the index costs more per entry than the design allows. It runs on every push, in release, with the figures printed into the log, and every map it builds takes a fixed seed so that two runs of one binary report the same bytes rather than a few per cent either way.
- **A RESP2 and RESP3 server, in `rugo-server`.** `GET SET SETEX PSETEX MGET MSET INCR DECR INCRBY DECRBY STRLEN DEL UNLINK EXISTS EXPIRE PEXPIRE EXPIREAT PEXPIREAT TTL PTTL PERSIST DBSIZE FLUSHALL FLUSHDB PING ECHO HELLO SELECT RESET QUIT INFO COMMAND CONFIG GET CLIENT`, over TCP and over a unix socket, with inline commands and pipelining. `SET` takes `EX PX EXAT PXAT KEEPTTL NX XX GET`. RESP2 and RESP3 differ in exactly two places, the null and the map, and both are tested byte for byte in `crates/rugo-server/tests/wire.rs`.
- **N threads, each with its own poller.** epoll on Linux, kqueue on the BSDs and macOS, level triggered, with the listeners in every thread's poller so whoever is free takes the connection and keeps it. `std` owns the accept, the read and the write; the unsafe is confined to the multiplexing syscall itself.
- **A connection is accepted one to a turn, so a burst of them is shared out between the threads.** A connection lives on the thread that accepted it for as long as it lasts, so how a burst is divided is how the load is divided. Every thread has the listener in its poller and every thread accepted until the listener blocked, which gave the whole backlog to whichever thread woke first, and a benchmark opens all its connections at once so that was every time. Measured on `gpc`, sixteen threads, two hundred and fifty-six connections at pipeline depth twenty-five over a unix socket with values of one to one thousand and twenty-four bytes: before the change one thread ran at 98 per cent of a core, five sat at three and a half, and the process used four and a half of its sixteen; after it, the busiest thread is at 48 and the quietest at 32. On that same load throughput went from 8.27 to 11.25 million operations a second and average latency from 1.250 to 0.583 milliseconds. That is a shape of load rather than a profile, so it is a before-and-after against itself and not a number to compare with anything else.
- **A connection is re-registered with the poller only when what it wants has changed.** It used to be re-registered every turn, on the reasoning that tracking the last interest was state that could go wrong. It is one field written in one place, the accepting side reads it rather than keeping a second copy of the same constant, and both pollers are level triggered so what was asked for last is what is still in force. In the steady state a connection reading commands and answering them wants next what it wanted last, so the `epoll_ctl` was one of the three syscalls a batch made and it restated a fact the kernel already held. No throughput number is claimed for this: the change removes a syscall per batch, and what that is worth is for a sweep to say. The path it could have broken — a reply too large for the socket to take in one write, which has to ask for writability and then ask its way back — had no test, and now has one that fails when the re-registration is removed.
- **A lookup asks for the slot before it knows which slot it wants.** A probe reads two arrays that live in different allocations, and past a few million keys both reads miss. Only the first can start on its own: the lane a slot is read from falls out of comparing the tag against the control bytes, so the slot load waits for the control load and the entry load waits for the slot, which is three misses end to end for one key. The address of the group of slots is known before the lane is, because the lane only picks which of the sixteen to read and they are contiguous, so a prefetch issued before the control load lets the second miss run underneath the first and leaves two on the path rather than three. Measured on `server3` with user space counters, one thread, pipeline depth twenty-five over a unix socket, five million keys of one to a thousand bytes and every lookup hitting: 5832 cycles an operation against 6999, four runs each, interleaved, every pair in the same direction. The count of cache misses does not move, which is the point of it. It costs five instructions an operation out of twelve hundred. On a run where five in six lookups miss, where the hint is spent on a group that turns out to hold nothing, it is 2672 against 2746, so the case it cannot help is still not a case it hurts.
- **A reference resolves without reading a second allocation first.** Getting to an entry is four loads and each one has to wait for the one before it: the control bytes give a slot, the slot gives an arena reference, the reference names a segment, and only once the segment is in hand does the entry have an address. The third of those read a `Vec`, which is a heap allocation per shard, and at four thousand shards that is a quarter of a megabyte of scattered cache lines carrying one pointer and one length each, which a workload streaming gigabytes of values through the cache evicts continuously. The first four segments now sit in the arena itself, which is one cache line, in the same allocation as the table that owns it and a few lines from the control bytes the same lookup has just read. Segments double in size, so the fifth is reached only past fifteen megabytes in a single shard, which at the usual shard count is a cache in the tens of gigabytes; past that they go in a `Vec` as before. Measured on `server3` with user space counters, one thread, pipeline depth twenty-five over a unix socket, five million keys of one to a thousand bytes and every lookup hitting: 4882 cycles an operation against 5517, eight runs each, interleaved, every pair in the same direction. Cache misses fall from 41.4 an operation to 38.8, which is the removed load itself. It costs six instructions an operation out of twelve hundred. On a run where five in six lookups miss it reads 2497 against 2632 over three pairs, but one of the three went the other way and the box was not quiet by then, so that half is a direction rather than a figure.
- **A lookup asks for its cache lines while the commands in front of it are still being answered.** A get is three loads that depend on each other: the control bytes say which lane, the lane says which slot, the slot says where the entry is. Past the last level of cache that is three misses that cannot overlap, because each address comes out of the load before it, and that latency rather than any instruction count is most of what a lookup costs. They can overlap across commands though, and a pipelined client has already sent the next several, so their keys are sitting in the read buffer waiting to be read off it. A connection now looks ahead over up to eight whole commands before it runs any of them, asks the map for each key's index line, asks again for each key's entry line, and then executes them one at a time exactly as it did before. The looking is not a parse: it walks the framing, keeps the one span that is the key and builds nothing, so the connection still has exactly one argument list alive at a time. Holding a parsed command per look-ahead step instead is the obvious way to write this and it was slower than not looking ahead at all, which is in [PERFORMANCE.md](PERFORMANCE.md) with its numbers. Measured on `server3` with user space counters, pipeline depth twenty-five over a unix socket, five million keys of one to a thousand and twenty-four bytes, which is the shape the sweep sends, every lookup hitting, and the binaries run in alternation because that box is shared. At four threads, gets cost 2859 cycles an operation against 3815, over three rounds with every round in the same direction. Sets, which look a key up before they write it, cost 3039 against 3827 over two rounds. At one thread the same shape reads 3036 against 3581 over four rounds, three of the four in that direction and the fourth against it by eight per cent, which is what that box's spread looks like at one thread rather than a result that disagrees. On values of one to eight bytes at one thread, where the value copy is no longer most of the work, it is 1859 against 2679 over three rounds. The count of cache misses barely moves in any of them, 35.2 an operation against 36.0 at four threads and 32.2 either way on sets, which is what asking early is supposed to look like: the same lines are fetched and they are fetched sooner. It costs about four hundred and ninety instructions an operation out of twelve hundred, which is the second walk over the framing and the two extra hashes a key.
- **The sweep does not walk a shard that has nothing in it to expire.** Each table now counts how many of its entries carry an expiry, so a shard where nothing was given a TTL is skipped without reading anything. The walk it replaces asked every full slot when it expired, and the only place that answer is written is the entry itself, so asking meant a read of the arena at an unrelated offset a couple of hundred times a call to be told the same nothing. The count is exact rather than a hint, so a shard that does hold a timed entry is swept exactly as before, and every site that can change the answer already has the entry header in hand for its own reasons. Measured on `server3` in the shape above, the walk is eighteen instructions an operation out of twelve hundred. What that is worth in cycles is inside the run to run spread of that box, so no cycle figure is claimed for it.
- **A second serving loop on Linux, on io_uring, behind `--uring`.** A poller is told a socket is readable and the thread then reads it, which is two syscalls for one read and three for a batch that also answers. A ring is given the read before the bytes exist and the completion is the bytes having arrived, so a connection serving a pipeline makes no syscall of its own at all and one `io_uring_enter` a turn carries every connection's read and every connection's write together. A connection has one operation outstanding and submits the next when that one completes, which is what makes handing the kernel a raw buffer address safe: between a submission and its completion nothing touches either buffer, so neither can be grown, compacted or freed while the kernel is writing into it. Accepts are armed one a listener and re-armed as they complete rather than armed multishot, because a connection lives on the thread that accepted it and a multishot accept lets whichever ring the kernel reaches first take the whole backlog, which is the load of the whole server decided by a race and the same mistake the readiness loop made before the accept fix above. The hundred millisecond tick the poller gets from its wait timeout is a timeout operation here, since a ring has no timeout argument to wait on. The ring itself is in `rugo-net`, written against the kernel ABI with no io_uring crate under it, which is five structures, three syscalls and three mappings. `--uring auto` takes a ring where the kernel offers one, `yes` refuses to start where it cannot, and `no` keeps the poller. No throughput figure is claimed for it: the two loops have not been measured against each other, and the sweep that does that is what decides whether `auto` should keep meaning what it means. What is claimed is that they answer the same bytes, and that is a test rather than a reading. The wire suite runs its whole script through both loops and compares the two transcripts.
- **`SCOREBOARD.md`, generated by `cargo xtask scoreboard`.** It is written from the sweep files committed in `bench/` and checked on every push, so a ratio cannot be typed in by hand. It currently carries one measurement, of memory, and says in as many words that throughput was not measured, rather than leaving a reader to assume the missing half.

### Known gaps

- **No published throughput numbers, and the sweep that produced the first ones has been withdrawn.** rugo is cache-bench's eighth subject, both bench hosts are provisioned, and a `wsl32coarse` sweep on `gpc` ran far enough to give a first reading: against pogocache rugo read between 0.63 and 0.83 at one thread and between 0.10 and 0.47 at eight and sixteen. Those numbers are not being carried forward. That sweep records the one minute load average before every attempt, and over the cells it measured the median was 18.9 for pogocache, 18.2 for dragonfly, 16.1 for valkey, 14.2 for redis and 13.4 for memcached, against 5.7 for rugo. A comparison where the subject got the quiet hours and the rivals got the busy ones is one that flatters the subject, so the direction of the error is towards rugo rather than away from it, and the honest thing to do with it is to throw it away rather than to quote it with a caveat. The box also restarts every few minutes under load it does not control, which is why the sweep never finished. The sweep the first published number will come from is `epyc8coarse` on `server3`, which is a coarse trim of the `epyc8` matrix added to cache-bench for this, and it is running now. Nothing has gone into `SCOREBOARD.md` yet, because a scoreboard row is generated from a committed sweep.
- **The memory gate is not met against Dragonfly.** Measured on `gpc` at ten million keys, rugo's overhead is 20.4 bytes an entry against Garnet's 245.6, memcached's 139.3, Redis's 111.8, Valkey's 100.8, pogocache's 88.8 and yo's 43.3, all of which clear the factor of two. Dragonfly at 31.7 is 1.55x and does not. Halving it needs 15.8, which is under what the index costs at this shape plus the entry header plus the grain, so the row does not move without one of those three getting cheaper rather than by tuning.
- **The two serving loops have not been measured against each other.** The ring is the default on a kernel that has one, and which of the two is faster on this workload is a question a sweep has to answer rather than a thing the shape of the loop settles. Until it has, `--uring no` is there and the poller is the one every published number was taken with.
- **One eviction rule and no choice of rule.** Under `--maxmemory` the map draws two entries at random and drops whichever expires sooner, an entry with no expiry counting as expiring last. That is a deliberate trade — a true recency order costs two links an entry, and sixteen bytes of links on a five byte slot would undo the thing this map exists for — but it is one rule where Redis offers eight, and `maxmemory-policy` is not settable. Whether it is the right rule is a question for a sweep.
- **No Windows.** The poller is epoll and kqueue and the listener is a unix socket; the Windows equivalent is IOCP, which is a second server rather than a build of this one. The crates below the server are portable and CI builds and tests them on Windows so a change that only compiles on one target is caught, but there is no Windows binary in a release and there is no plan for one.
- **No authentication and no TLS.** `M6`.
